# Signal — собственный чат с голосом и видео

Собственный чат для браузера, Windows 10/11 и Android 5.0+ с голосом, видео и передачей экрана: личные аккаунты, каналы, история сообщений, присутствие, голос, камера и демонстрация экрана. Регистрация открыта и не требует приглашения. У нового аккаунта нет каналов; любой пользователь может создать свой канал и стать владельцем либо принять приглашение в чужой. Ссылка добавляет участника на указанный сервер с доступом к его текстовым и голосовым каналам после входа и подтверждения. История, сообщения, звонки и события доступны участникам канала. Медиа передаёт собственный LiveKit SFU без перекодирования. Комната рассчитана на 10 участников. Пользователи и переписка хранятся в SQLite на сервере.

На главной находятся друзья, запросы по никнейму с принятием и отказом, личная переписка и звонок с ответом или отклонением. Слева — серверы, внутри каждого можно создать несколько текстовых и голосовых каналов. Старые группы перенесены в отдельные серверы с прежними участниками и историей. Приглашение теперь открывает весь сервер; права и блокировки распространяются на его каналы. Старый Android 0.1.2 сохраняет совместимость.

Настройки звонка открываются в прокручиваемой панели справа. Возле никнейма — микрофон и наушники; вне подключённого звонка они недоступны. Нижняя шестерёнка выбирает одну из шести цветовых тем, выбор сохраняется на устройстве.

Ключ медиа выдаёт и знает сервер приложения; медиасервер LiveKit его не получает. Текстовые чаты этим механизмом не шифруются.

## Android-клиент

В каталоге `android/` находится приложение для Android 5.0–17 (API 21–37). Интерфейс аккаунта, каналов и переписки включён в APK; данные и связь используют ваш сервер. Нативный LiveKit-клиент обеспечивает голосовой канал до 10 участников, камеру, полный экран камеры и трансляции, переключение камеры, гарнитуру и звонок через фоновую службу с уведомлением. Показ экрана поддерживает исходное разрешение, 30/60 fps, 12/24/40 Мбит/с и H.264/VP9/VP8. Звук разрешающих захват приложений вместе с микрофоном доступен с Android 10, на Android 5–9 передаются экран и микрофон. Нужен WebView Chromium 94+; APK включает ARM32, ARM64 и x86_64. Для каждого запуска захвата Android запрашивает системное подтверждение. Кодеки используют сжатие с потерями; реальное качество и FPS зависят от телефона, сети и VPN.

Сборка: Node.js 24, pnpm 11.25.0, JDK 21, Android SDK Platform 37.0 и Build Tools 37.0.0, включённый Gradle Wrapper 9.8.1 и Android Gradle Plugin 9.4.1. Из корня выполните `pnpm install --frozen-lockfile`, `pnpm build:android`, затем `./android/gradlew.bat -p android lintDebug assembleDebug`. GitHub Actions автоматически собирает устанавливаемый debug APK; постоянный подписанный выпуск и обновления используют один сохранённый ключ. APK, ключи и пароли не хранятся в Git. Подробности установки, сборки, четырёх secrets для release в Actions и обновлений: [android/README.md](android/README.md). Сквозная проверка на физических телефонах Android 5.0–17 ещё не проведена.

В профиле можно скопировать username. Приглашение по username приходит во входящие; получатель принимает или отклоняет его, после отказа можно сразу отправить новое.

Роли канала: владелец, администратор, участник. Владелец назначает и снимает администраторов и удаляет канал; владелец и администраторы меняют настройки и приглашают людей. ## Оценка вашего VPS

На предоставленных скриншотах: 2 vCPU Intel Xeon E5-2699 v4, около 4 ГБ RAM. В панели VPN CPU 12% (на показанном отрезке пик 21%), память 751,69 МБ из 3,82 ГБ. На диске свободно 51,75 ГБ; карточка тарифа показывает другой объём, поэтому фактическую ёмкость следует уточнить на сервере. Указание «до 10 Gbit/s» — верхний предел тарифа, оно не измеряет доступную полосу или маршрут до пользователей.

**Такой сервер подходит для пробного запуска чата и комнаты на 10 человек. Стабильное одновременное видео 1080p от всех 10 вместе с VPN пока не подтверждено.** Запас памяти выглядит достаточным для выбранной схемы без записи и перекодирования. Остаются неизвестными пиковая нагрузка VPN, ограничения CPU у провайдера, скорость порта, потери UDP и задержки маршрутов. Статистика одного скриншота не покрывает эти условия.

Оценка трафика для случая, когда все видят все остальные 9 камер в полном качестве:

| Поток одной камеры | Вход на SFU (10 камер) | Выход с SFU (10 × 9 потоков) |
| --- | --- | --- |
| 2 Мбит/с | 20 Мбит/с | 180 Мбит/с |
| 4 Мбит/с | 40 Мбит/с | 360 Мбит/с |
| 6 Мбит/с | 60 Мбит/с | 540 Мбит/с |

Это арифметическая модель, не результат теста. К этим числам прибавляются звук, служебные пакеты, повторные передачи, варианты simulcast, демонстрация экрана и VPN. Для 4 Мбит/с стоит проверить хотя бы 450–500 Мбит/с устойчивого исходящего трафика со свободным запасом для VPN. Один час при 360 Мбит/с — примерно 162 ГБ исходящего трафика; уточните правила и лимит провайдера.

Нельзя гарантировать отсутствие сжатия, потерь разрешения и любую фиксированную задержку на интернете. WebRTC использует сжатие, а качество зависит от камеры, устройства и сети участника. SFU не перекодирует видео; при слабой сети клиент может получать меньший слой simulcast, снижать частоту кадров или временно приостанавливать видео. Полное качество для всех камер требует достаточной полосы у каждого клиента: при 4 Мбит/с на камеру ему нужно около 36 Мбит/с входа только для девяти видео.

Начальные ограничения контейнеров: LiveKit 1,25 CPU / 1 ГБ, приложение 0,3 CPU / 384 МБ, HTTPS 0,15 CPU / 128 МБ. Суммарный максимум — 1,7 CPU и 1,5 ГБ. Эти ограничения оставляют часть ресурсов VPN, но не гарантируют ему качество обслуживания. Слишком низкий CPU лимит сам повышает задержку, поэтому менять лимиты следует по результатам теста, включая показатели throttling и VPN.

## Схема

- Браузер → HTTPS Caddy → приложение и WebSocket API на `127.0.0.1:3000`.
- Браузер → HTTPS Caddy → LiveKit API/сигнализация на `127.0.0.1:7880`.
- Звук и видео → напрямую на LiveKit UDP `7882–7883`; запасной транспорт — TCP `7881`.
- SQLite хранится в отдельном Docker volume `signal_app-data`; сертификаты — в volumes Caddy.
- Linux host networking сохраняет прямую адресацию WebRTC. Этот комплект не рассчитан на Docker Desktop, rootless Docker или Kubernetes.

Никакие скрипты не редактируют Xray, не перезапускают VPN, не очищают firewall и не удаляют сторонние Docker объекты. Runtime ограничен отдельным Compose проектом `signal`. Подготовка Docker Engine и его влияние на сетевые правила требуют отдельной оценки, если Docker ещё не установлен на VPN сервере.

## Подготовка

Нужен Linux x86-64 VPS с Docker Engine и Compose v2. Понадобятся минимум 6 ГБ свободного места на сборку/образы и 1,8 ГБ доступной памяти на момент старта. Для первичной генерации конфига подходит Node.js 24 на вашей рабочей машине или временный контейнер Node на VPS.

Выберите один вариант адреса. Для доменного варианта создайте два DNS A имени, например `chat.ВАШ-ДОМЕН` и `rtc.ВАШ-ДОМЕН`, указывающие прямо на публичный IPv4 VPS. Адреса должны принадлежать вам. Не включайте DNS proxy/CDN для этих имён. Базовая конфигурация использует IPv4; AAAA записи требуют отдельной настройки IPv6 и по умолчанию блокируют доменную установку.

Для варианта без домена используется `https://<IPv4-VPS>:8443` и доверенный IP сертификат Let's Encrypt. С января 2026 года [такие сертификаты общедоступны и действуют 160 часов](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability). Генератор явно задаёт профиль `shortlived` в ACME issuer Caddy 2.11.7; Caddy отвечает за продление. IP должен быть вашим и оставаться выделенным VPS, TCP80 — доступным снаружи для каждого продления. В этом режиме тот же HTTPS адрес обслуживает LiveKit через пути `/rtc` и `/twirp/`; внешний DNS не требуется. Выдачу и автоматическое продление нужно проверить на целевом сервере. Обход предупреждений браузера не нужен.

Альтернативы вида sslip.io/nip.io используют внешний DNS сервис, не принадлежащий вам. Они добавляют зависимость от его доступности и правил; в конфигурации они не используются.

Проверьте свободные входящие порты на VPS и firewall провайдера:

| Порт | Назначение | Доступ |
| --- | --- | --- |
| TCP 80 | ACME HTTP challenge, автоматическое продление TLS | Интернет |
| TCP 8443 | HTTPS приложения и сигнализации | Интернет |
| TCP 7881 | Запасной WebRTC ICE/TCP | Интернет |
| UDP 7882–7883 | Основной транспорт медиа | Интернет |
| TCP 3000, 7880 | Внутренние API | Только loopback |
| UDP 3478 и 30000–30100 | Только при включении embedded TURN/UDP | См. ограничение TURN ниже |

Порт 443 здесь не используется: он часто занят Xray. По умолчанию HTTPS работает на 8443 и выдаёт обычный доверенный сертификат через HTTP challenge на 80. **Для этого именно публичный TCP80 должен быть доступен.** Если 80 уже занят вашим сервисом, скрипт остановится. Нужна интеграция с существующим reverse proxy либо DNS challenge; простая смена 80 на другой порт не решает проверку сертификата.

Команды ниже выполняются в папке проекта. Подставьте ваши реальные домены, IP и email вместо значений в угловых скобках. Сначала только прочитайте состояние VPS:

```bash
bash deploy/preflight.sh
```

Скрипт печатает загрузку, память, диск, слушающие порты, имена и расход ресурсов процессов VPN, сетевые счётчики. Он не читает конфиги VPN и не проводит сетевой стресс тест. Не публикуйте полный отчёт, если адреса или структура сети для вас чувствительны.

Создайте личный `deploy/.env`:

```bash
node deploy/generate-env.mjs --app-domain '<домен-чата>' --rtc-domain '<домен-rtc>' --server-ip '<IPv4-VPS>' --email '<ваш-email>'
```

Либо без собственного домена:

```bash
node deploy/generate-env.mjs --ip-only --server-ip '<IPv4-VPS>' --email '<ваш-email>'
```

Параметр `--email` необязателен: можно опустить его, если не хотите передавать контактную почту ACME центру сертификации. Не подставляйте фиктивный адрес.

Если Node нет на VPS, из папки `deploy` можно использовать Docker:

```bash
docker run --rm --network none --user "$(id -u):$(id -g)" --mount "type=bind,src=$PWD,dst=/config" --workdir /config node:24-bookworm-slim node generate-env.mjs --app-domain '<домен-чата>' --rtc-domain '<домен-rtc>' --server-ip '<IPv4-VPS>' --email '<ваш-email>'
```

Docker предварительно должен иметь образ Node локально (иначе сначала `docker pull node:24-bookworm-slim`). Генератор создаёт криптографически случайные пароль администратора и ключи LiveKit. Существующий `.env` он не перезаписывает. Права на секретные файлы — `0600`, папку generated — `0700`. Они исключены из Git и контекста сборки. Просматривайте пароль локально, не отправляйте `.env` в чат.

Для IP варианта в Docker команде замените `--app-domain ... --rtc-domain ...` на `--ip-only`. Не запускайте генератор повторно для смены адреса: отредактируйте адресные поля существующего `.env`, сохранив ключи.

Начальная установка:

```bash
bash deploy/deploy.sh
```

Скрипт снова проверит порты и минимальный запас ресурсов, проверит DNS в доменном режиме, создаст конфиги, проверит конфигурацию Caddy, соберёт приложение и запустит только этот проект. Сборка временно потребляет CPU и память сверх runtime лимитов; на загруженном VPN сервере безопаснее собрать `signal-app:local` на другой Linux x86-64 машине и перенести образ, после чего запустить `docker compose -f deploy/compose.yaml up -d --no-build`. Во время начальной установки нужны исходящие DNS/HTTPS подключения для образов, зависимостей и сертификатов.

Откройте `https://<домен-чата>:8443` либо `https://<IPv4-VPS>:8443` в IP режиме. Начальное имя — `admin`; имя и пароль находятся в `deploy/.env`. После первого запуска пароль хранится в БД в виде хеша. Простая правка `ADMIN_PASSWORD` в `.env` не меняет уже созданную учётную запись. Порт можно задать генератору `--https-port`, сохранив его свободным.

## Проверка после установки

```bash
docker compose -f deploy/compose.yaml ps
docker compose -f deploy/compose.yaml logs --tail=80 app livekit caddy
curl --fail https://<домен-чата>:8443/api/health
```

Ожидается `ok: true`, `mediaConfigured: true`, контейнер приложения healthy и доверенный HTTPS без исключений браузера. Поле `mediaConfigured` означает наличие конфигурации, не успешную проверку голосового соединения. Проверьте голос и камеру между двумя устройствами из разных сетей, демонстрацию экрана, повторное подключение и отказ одиннадцатому участнику. Разрешение и частоту кадров проверяйте в `chrome://webrtc-internals` на обоих концах. Проверьте доступность VPN в то же время.

Нагрузочный тест запускайте на другой машине с достаточной полосой, когда это допустимо для VPN. Используйте [официальный LiveKit CLI](https://docs.livekit.io/reference/developer-tools/livekit-cli/). Ключи передавайте локальными переменными окружения `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`; не помещайте секрет в историю команд. Сначала выполните `lk perf load-test --help`, чтобы проверить параметры установленной версии.

```bash
lk room create --empty-timeout 600 capacity-test
lk perf load-test --room capacity-test --video-publishers 5 --audio-publishers 5 --subscribers 5 --video-resolution high --duration 10m
```

Это начальная проверка пяти отправителей и пяти получателей, а не подтверждение нагрузки десяти камер. Генератор CLI создаёт отдельных publisher/subscriber участников, поэтому сочетание 10+10 может превысить лимит комнаты 10. Для итоговой проверки лимита и качества нужны 10 настоящих браузеров, каждый из которых одновременно отправляет и получает медиа. `high` в CLI не доказывает 1080p/30 для вашего приложения: встроенный контент/битрейт и число декодируемых клиентом видео могут отличаться. Сопоставьте реальное число подписок, битрейт и разрешения в статистике CLI и браузера.

Во время теста наблюдайте `docker stats`, `vmstat 1`, сетевой трафик, потери пакетов, RTT/jitter и VPN из отдельного клиента. CPU желательно держать с запасом, без постоянного throttling и memory pressure. Рост потерь или задержки VPN — основание уменьшить видео битрейт/количество камер, снять нагрузку с VPS либо выделить SFU отдельный сервер. Результаты тестов на иных машинах из документации LiveKit не подтверждают мощность этого VPS.

## Ограничение TURN

В базовом варианте доступны UDP и прямой ICE/TCP7881. Для некоторых корпоративных сетей и мобильных операторов этого недостаточно. `TURN_ENABLED=true` включает встроенный TURN/UDP3478; TCP/TLS он не добавляет. Изменение нужно отрендерить и проверить порты заново, затем перезапустить только LiveKit. UDP relay диапазон 30000–30100 должен не конфликтовать с другими сервисами; проверка доступности нужна с внешних клиентов.

Для сетей, разрешающих только TLS443, нужен отдельный TURN/TLS443 с сертификатом и проверкой совместимости с вашим Xray — обычно отдельный IP/VPS или согласованный L4 proxy. HTTP reverse proxy Caddy сам по себе не реализует TURN/TLS. Фиктивный TLS TURN endpoint здесь не объявлен. Без этой дополнительной настройки доступность во всех сетях не гарантируется.

## Остановка, обновление, резервная копия

Остановка только этого проекта с сохранением данных:

```bash
docker compose -f deploy/compose.yaml stop
```

Согласованная копия SQLite (скрипт ненадолго остановит только приложение, затем восстановит его предыдущее состояние):

```bash
bash deploy/backup.sh
```

Копии появляются в `deploy/backups/` и включают содержимое `/data`. Копирование живого SQLite файла без согласования WAL может дать неполную БД; используйте этот скрипт или штатный SQLite backup API. Храните `deploy/.env` в отдельной защищённой резервной копии, а копии БД — также за пределами VPS. Перед восстановлением остановите приложение и восстановите файлы в его volume с владельцем UID1000; конфигурацию и восстановленную БД сначала проверьте в отдельном окружении.

Обновление: создайте резервную копию, сохраните прежний образ `signal-app:local` отдельным тегом, перенесите новые исходники и соберите приложение. Затем:

```bash
docker compose -f deploy/compose.yaml build app
docker compose -f deploy/compose.yaml up -d --no-build app
```

Не удаляйте volumes при обновлении. Версия SFU закреплена на `livekit/livekit-server:v1.13.10`; перед её сменой проверьте release notes и совместимость SDK. Caddy закреплён на `2.11.7-alpine`. Образы следует обновлять осознанно вместе с проверкой уязвимостей; теги Node24 получают исправления при новой сборке. Не используйте серверный `docker system prune` для обслуживания этого приложения.
